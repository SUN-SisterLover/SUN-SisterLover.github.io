## 5.1 子系统的启动与终止

这一节主要讨论游戏引擎中不同子系统的启动顺序与关闭顺序：例如先启动日志系统，再启动渲染/战斗等业务系统。

### 5.1.1 C++ 的静态初始化顺序（不可靠）

C++ 在进入程序入口点 `main()` 或 `WinMain()` 之前，全局对象与静态对象就可能已经被构造；而这些构造函数的调用顺序在不同编译单元之间**无法可靠预测**。当 `main()`/`WinMain()` 返回后，全局/静态对象会被析构，析构顺序同样难以保证。

因此，**不建议**依赖“全局/静态对象的构造与析构”来初始化或终止游戏引擎的各个子系统。

一般来说，这类管理器常用单例实现；如果把“启动逻辑写在构造函数里、关闭逻辑写在析构函数里”，那么它的启动/关闭时机就会被静态初始化与析构顺序牵着走，程序侧几乎无法精确控制。

#### 按需构建
函数内部的静态变量不会早于 `main()` 构建，而是在**第一次执行到该语句**时才构造（常见做法即 “Meyers Singleton”）。因此可以把“全局单例对象”改为“函数内静态对象”，从而用调用顺序控制构建顺序。

例如提供 `static RenderManager& Get()`，通过 `Get()` 获取实例；若某个管理器依赖另一个管理器，可以在其初始化路径中显式调用 `OtherManager::Get()` 来确保依赖先被构造。

但这种做法仍然**无法精确控制析构顺序**；同时也很难统一把“初始化成本”集中在可控的启动阶段（首次调用时可能产生明显开销）。

### 5.1.2 一个行之有效的简单做法：显式启动/终止

仍然可以保留“单例/管理器”的概念，但把真正的生命周期管理从构造/析构中剥离出来：

- **构造/析构**：尽量不做启动/关闭工作（或只做极轻量的默认初始化）。
- **显式接口**：提供 `StartUp()` 与 `ShutDown()`（注意大小写统一）来管理资源。

在 `main()` 中按正确顺序执行（伪代码）：

1. `ManagerA::Get().StartUp()`
2. `ManagerB::Get().StartUp()`
3. `Run()`
4. `ManagerB::Get().ShutDown()`
5. `ManagerA::Get().ShutDown()`

也可以做成“注册表/队列”的形式：各子系统注册自己的启动优先级与依赖关系，由统一的启动器按拓扑排序或优先级顺序启动与关闭。

## 5.2 内存管理

内存对性能的影响主要有两方面：

1. **分配/释放成本**：使用 `malloc()` 或 C++ 全局 `new` 进行动态内存分配通常较慢。想提升性能，要么尽量避免频繁的动态分配，要么使用定制分配器降低成本。
2. **访问局部性**：在现代 CPU 上，性能很大程度受内存访问模式影响。把数据放在**小而连续**的内存块中，通常远比分散在大量地址空间中更缓存友好、更高效。

### 5.2.1 优化动态内存分配

使用 `malloc()/free()`（或 C++ 的全局 `new/delete`）进行堆分配通常比较慢，常见原因包括：

1. **通用性带来的管理开销**：通用堆分配器需要处理不同大小、不同生命周期的请求，会维护大量元数据并进行复杂的管理与合并/分裂。
2. **同步与系统交互成本**：分配器往往需要加锁/同步；并且在某些场景下可能需要向操作系统申请/归还页等资源（注：不一定每次 `malloc()` 都进入内核，但总体上与系统交互、同步与碎片管理都会带来成本）。

游戏开发中常见经验法则：**将堆分配维持在最低限度，并且避免在紧凑循环（hot loop）中进行堆分配**。

但在无法完全避免动态分配时，通常会实现一个或多个定制分配器。其性能优势往往来自：

- **预分配内存池**：从预先申请的一大块内存中满足请求（这块内存可能来源于一次性的 `malloc/new`，或静态/全局缓冲区）。
- **针对特定使用模式优化**：对分配大小、对齐、释放方式（如批量释放/回滚）等做出假设，从而比通用堆分配更高效。

下面介绍几种常用的定制分配器。

#### 5.2.2 基于堆栈（Stack）的分配器

**应用场景**：加载新关卡时需要为该关卡分配大量内存；关卡加载完成后，运行期很少（甚至不会）再进行分配；当关卡结束时，整体卸载并释放这批内存。此时非常适合用“堆栈/线性分配 + 回滚（marker）”的方式管理。

堆栈分配器通常易于实现：预留一块连续内存，并维护一个“顶端指针”。分配时指针前进；释放时可以**回滚到某个标记**或直接清空。

一个典型接口（伪代码）如下：

```cpp
class StackAllocator {
public:
  using Marker = uint32_t; // 表示堆栈的当前顶端（偏移/标记）

  // 给定总大小，构建一个堆栈分配器
  explicit StackAllocator(uint32_t stackSizeBytes);

  // 从堆栈顶端分配一个新的内存块
  void* Alloc(uint32_t sizeBytes);

  // 取得当前堆栈顶端标记
  Marker GetMarker() const;

  // 回滚到之前的标记
  void FreeToMarker(Marker marker);

  // 清空整个堆栈
  void Clear();
};
```

#### 5.2.3 双端堆栈（Double-Ended Stack）分配器

**思路**：一块连续内存同时供两个“线性/堆栈”分配器使用：

- **底端堆栈**：从低地址向高地址增长（Bottom → Up）
- **顶端堆栈**：从高地址向低地址增长（Top → Down）

只要两端的“顶端指针”不相撞，就能共享同一块缓冲区，从而更充分地利用内存。

**应用场景**（常见组合）：

- 一端负责**关卡/资源加载期**的大块、生命周期较长的分配（关卡结束整体回滚）
- 另一端负责**每帧临时内存**（frame temp），在帧结束时整体清空/回滚

这种模式的好处是：生命周期模式非常明确，几乎不产生外部碎片；并且“按阶段整体回收”非常便宜。

一个典型接口（伪代码）：

```cpp
class DoubleEndedStackAllocator {
public:
  using Marker = uint32_t;

  explicit DoubleEndedStackAllocator(uint32_t totalBytes);

  // 底端：向上增长
  void* AllocBottom(uint32_t sizeBytes);
  Marker GetBottomMarker() const;
  void  FreeBottomToMarker(Marker marker);
  void  ClearBottom();

  // 顶端：向下增长
  void* AllocTop(uint32_t sizeBytes);
  Marker GetTopMarker() const;
  void  FreeTopToMarker(Marker marker);
  void  ClearTop();
};
```

**注意点**：

- 两端分配时都要检查是否越界（Bottom/Top 指针不能交叉）。
- 仍然更适合“批量回滚/阶段性清空”，而不是任意顺序释放。

#### 5.2.4 池（Pool）分配器

**应用场景**：在游戏引擎开发中经常要分配大量**同尺寸**的小块内存，例如：粒子、子弹、链表节点、迭代器、可渲染对象实例等。此时用池分配器可以把分配/释放变成非常稳定且快速的操作。

**核心思想**：先预分配一整块内存，把它切成 \(N\) 个等大的“元素块”（element）。之后：

- **分配**：从空闲列表（free list）拿出一个元素块返回
- **释放**：把元素块再塞回空闲列表

因为每次只改动很少的指针/索引，所以分配与释放通常都是 \(O(1)\)。

**free list 的 `next` 指针存哪里？**

- 如果 `elementSize >= sizeof(void*)`，可以直接把 `next` 指针**存进空闲元素块自己的内存里**（空闲时本来就没有有效对象数据），这样不需要额外开销。
- 如果 `elementSize < sizeof(void*)`，则可以用“元素索引”代替指针来实现 free list，例如用 16 位索引作为 `next`，只要池内元素数量不超过 \(2^{16} = 65536\) 即可。

一个典型接口（伪代码）：

```cpp
class PoolAllocator {
public:
  explicit PoolAllocator(uint32_t elementSizeBytes, uint32_t elementCount);

  void* Alloc();
  void  Free(void* p);

  void  Clear(); // 重新构建 free list（把所有元素标为空闲）
};
```

#### 5.2.5 含对齐功能的分配器（Aligned Allocator）

很多平台/指令对内存对齐有要求或强烈偏好。例如 SIMD 数据、缓存行对齐、某些 DMA/平台 API 传输缓冲等。此时我们需要一个“在任意分配器之上”提供对齐能力的包装器：对外返回**已对齐的地址**，对内仍能正确释放。

**核心问题**：底层分配器返回的原始地址 `raw` 通常不保证满足 `alignment`。我们要在 `raw` 的基础上算出一个 `aligned`，并且在 `free(aligned)` 时能够找回 `raw`。

**1）如何从 `raw` 算出 `aligned`**

常见做法：先多申请一点空间，然后把地址向上“抬”到下一个对齐边界。

设 `alignment` 为 2 的幂（例如 16/32/64），则：

- `mask = alignment - 1`
- `misalignment = raw & mask`（raw 低位偏离量）
- `adjustment = (misalignment == 0) ? 0 : (alignment - misalignment)`
- `aligned = raw + adjustment`

等价写法（更常见）：

- `aligned = (raw + mask) & ~mask`

**2）释放时如何找回 `raw`**

释放时只拿到 `aligned`，因此需要把一些元信息（meta-information）存起来。图里采用的方式是：

- 把 `adjustment` 写到 `aligned` 前面的 1 字节（或若对齐更大/要求更严格，则写 2/4 字节）。
- 释放时读出这个 `adjustment`，计算 `raw = aligned - adjustment`，再交给底层分配器释放。

这种方法的前提是 `adjustment < 256`（1 字节能存下）。当 `alignment <= 128` 时通常成立。

一个典型接口（伪代码）：

```cpp
void* AllocateAligned(size_t sizeBytes, size_t alignment) {
  // alignment 必须是 2 的幂
  const size_t mask = alignment - 1;

  // 多申请一点：用于向上对齐 + 存 adjustment
  const size_t expandedSize = sizeBytes + alignment;

  uintptr_t raw = reinterpret_cast<uintptr_t>(AllocateUnaligned(expandedSize));
  uintptr_t aligned = (raw + mask) & ~static_cast<uintptr_t>(mask);

  size_t adjustment = static_cast<size_t>(aligned - raw);
  // 这里用 1 字节存 adjustment（和图里的做法一致）
  auto* pAligned = reinterpret_cast<uint8_t*>(aligned);
  pAligned[-1] = static_cast<uint8_t>(adjustment);

  return reinterpret_cast<void*>(aligned);
}

void FreeAligned(void* pMem) {
  auto* pAligned = reinterpret_cast<uint8_t*>(pMem);
  const size_t adjustment = static_cast<size_t>(pAligned[-1]);

  uintptr_t aligned = reinterpret_cast<uintptr_t>(pMem);
  uintptr_t raw = aligned - adjustment;
  FreeUnaligned(reinterpret_cast<void*>(raw));
}
```

**注意点**：

- `alignment` 一般要求是 2 的幂，否则位运算方案不成立。
- `expandedSize` 至少要保证“对齐调整空间 + 元信息空间”，上面写法用 `+ alignment` 是常见的简化。
- 若可能出现 `adjustment >= 256`（例如更大的对齐），就不能只存 1 字节，需要改存 2/4 字节或改用更通用的 header。


#### 5.2.6 单帧（Single-Frame）与双缓冲（Double-Buffered）内存分配器

几乎所有游戏引擎都会在主游戏循环中分配一些**临时数据**：这些数据只在一帧内使用，或者最多跨一帧用于“上一帧→下一帧”的衔接。对这种明确生命周期的内存，如果还走通用堆分配，不仅慢，还容易造成碎片和难以追踪的泄漏。

这一节介绍两种非常常见的“帧临时内存”分配模式：**单帧分配器**和**双缓冲分配器**。

##### 单帧分配器（single-frame allocator）

**思路**：预留一块内存，用一个简单的线性/堆栈分配器（例如上面的 `StackAllocator`）管理。每帧开始（或结束）时把指针重置，等价于把这一帧分配的所有临时内存“一键释放”。

**主循环伪代码**：

```cpp
StackAllocator g_singleFrameAllocator;

while (true) {
  // 每帧清空单帧分配器（相当于释放上一帧所有临时内存）
  g_singleFrameAllocator.Clear();

  // ...

  // 从单帧分配器申请临时内存
  void* p = g_singleFrameAllocator.Alloc(nBytes);

  // 重要：p 指向的数据只能在本帧内使用
  // ...
}
```

**优点**：

- 分配非常快，释放几乎为零成本（一次 `Clear()`）。
- 临时内存不会产生碎片，且易于控制“每帧临时内存上限”。

**最大缺点**：

- 分配出来的内存块**只在当前帧有效**。程序员必须自律：不能把指针缓存到跨帧结构中，也不能把它交给异步任务在下一帧继续写。

##### 双缓冲分配器（double-buffered allocator）

单帧分配器的限制是“严格一帧内有效”。但实际工程里经常存在“**第 i 帧分配，给第 i+1 帧使用**”的需求，例如：

- 渲染/提交线程之间的跨帧数据交接
- GPU/驱动提交队列的延迟
- 多核并行任务在下一帧才能被消费的结果缓冲

**思路**：准备两块等大小的“单帧缓冲”，帧与帧之间交替使用：

- 第 \(i\) 帧写入 Buffer A，同时读取（或保留）Buffer B 的内容
- 到第 \(i+1\) 帧交换 A/B，新的“当前缓冲”清空后继续分配

这样就允许“上一帧分配的数据在下一帧仍然可用”，但最多跨一帧。

**一个典型结构（伪代码）**：

```cpp
class DoubleBufferedAllocator {
  uint32_t m_cur = 0;
  StackAllocator m_stack[2];

public:
  void SwapBuffers() { m_cur = 1u - m_cur; }
  void ClearCurrentBuffer() { m_stack[m_cur].Clear(); }
  void* Alloc(uint32_t nBytes) { return m_stack[m_cur].Alloc(nBytes); }
};
```

**主循环伪代码**：

```cpp
DoubleBufferedAllocator g_doubleBufAllocator;

while (true) {
  // 交换缓冲：上一帧的“当前缓冲”变为“上一帧缓冲”
  g_doubleBufAllocator.SwapBuffers();

  // 清空新的当前缓冲，准备本帧分配
  g_doubleBufAllocator.ClearCurrentBuffer();

  // ...
  void* p = g_doubleBufAllocator.Alloc(nBytes);
  // p 指向的数据可用于本帧，且通常也允许在下一帧被读取
  // ...
}
```

**注意点**：

- 双缓冲并不等于“随便跨帧用”。它只把可用期从“1 帧”扩展到“最多 2 帧”，仍然需要明确约束数据的读写边界。
- 对异步任务（例如某任务在第 \(i\) 帧启动，第 \(i+2\) 帧才结束）的结果缓冲，双缓冲可能不够，需要更多缓冲（triple buffering）或任务专用分配器/池。

### 内存碎片
